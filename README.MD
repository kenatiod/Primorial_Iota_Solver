# Primorial Iota Solver

A Python implementation for finding the least prime-smoothness level attained by a product of two consecutive integers in each primorial interval. The repository contains the current solver **`Primorial_iota_Solver_v2_1.py`** and an **older solver's archived results** in `Iota_min_Solver_runs/`. The archived JSON files were generated by `Iota_min_Solver v2`, **not** by the included `Primorial_iota_Solver_v2_1.py`; they have a different output schema. The current file still prints internal version `v2.0` and has older filename examples in its docstring; the `v2_1` change from the neighboring `v2_0` file was table-column formatting.

## The quantity being computed

Let $p_j$ be the $j$th prime and $P_n=\prod_{j=1}^{n}p_j$ the $n$th primorial. For an integer $t>1$, let $\operatorname{gpf}(t)$ be its greatest prime factor, and let $\pi(p_j)=j$. Define

$$\iota_{\min}(n)=\min_{P_n\le m(m+1)<P_{n+1}}\pi\!\left(\operatorname{gpf}(m(m+1))\right),\qquad m\ge1.$$

Thus $\iota_{\min}(n)$ is the smallest index $s$ such that *some* consecutive pair $m,m+1$ in the $n$th product interval consists entirely of numbers with prime factors among $2,3,\ldots,p_s$. It is **not** a count of prime factors and is **not** necessarily equal to $n$. For example, $P_4=210$, $P_5=2310$, and $m=15$ gives $m(m+1)=240$ with greatest prime factor $5=p_3$; consequently $\iota_{\min}(4)=3$ (the lower levels must also be excluded to prove equality).

The code calculates interval bounds $L_n\le m\le U_n$ using exact integer square roots, where $L_n$ is the first $m$ with $m(m+1)\ge P_n$ and $U_n$ the last with $m(m+1)<P_{n+1}$.

## Why Pell equations find the candidates

Set $x=2m+1$. The identity

$$x^2-1=4m(m+1)$$

allows us to take $D$ as the squarefree part of $4m(m+1)$ and write $4m(m+1)=Dy^2$. This gives the Pell equation $x^2-Dy^2=1$. If both $m$ and $m+1$ are $p_s$-smooth, then every prime dividing $D$ belongs to $\{p_1,\ldots,p_s\}$. Conversely, the solver checks the actual factors of $m$ and $m+1$ before recording a candidate; a Pell solution alone does not prove smoothness.

For every squarefree $D>1$ made from the allowed primes, all positive Pell solutions are powers

$$x_k+y_k\sqrt D=(x_1+y_1\sqrt D)^k,$$

where $(x_1,y_1)$ is the fundamental solution. The code enumerates $D$ by the index of its largest prime factor (its **D-level**). At level $s$, it visits the $2^{s-1}$ squarefree products containing $p_s$ and any subset of the preceding primes, pruning those too large to fit the search window. A prospective $m$ is $p_s$-smooth precisely when neither member of the pair has a prime factor above $p_s$; the *actual* level can be higher than the D-level because factors of $y_k$ can introduce further primes.

The finite search window gives $x=2m+1\le C=2U_N+1$ for all requested intervals $n\le N$. Each Pell solution of $x^2-Dy^2=1$ is a continued-fraction convergent of $\sqrt D$; its numerators increase. Hence the fundamental-solution search may stop as soon as the next convergent numerator exceeds $C$: no solution for that $D$ can occur in this window. The code also discards $D>C^2$, since a positive Pell solution would require $D<x^2\le C^2$. It iterates powers until $x_k>C$ (and applies an additional index bound based on primitive divisors of Lucas sequences). If the fundamental $y_1$ contains an out-of-range prime, every $y_k$ does too because $y_1\mid y_k$, so that branch can be skipped.

For each odd $x_k$, the code sets $m=(x_k-1)/2$, checks $m$ and $m+1$ for smoothness with respect to the configured prime list, obtains their actual greatest-prime index, and assigns $m(m+1)$ to the interval by binary search. Duplicate $m$ values are removed. `omega` in the hit records counts **distinct** prime factors of $m(m+1)$; `pc=1` means `omega == level`, equivalently the radical of the product is $P_{\text{level}}$ (a *prime-complete* hit).

### What a completed level certifies

After all D-levels $1,\ldots,s$ have completed **without processing errors**, every pair with actual level at most $s$ within the size cap has been considered. Thus a recorded interval witness with actual level $\ell\le s$ proves $\iota_{\min}(n)=\ell$; no such witness proves $\iota_{\min}(n)\ge s+1$. A witness at a higher actual level is merely an upper bound until the intervening D-levels have completed. This is why a found pair is not automatically a proved minimum.

## Running the included solver

Python 3.9+ is needed for the built-in collection type annotations. `gmpy2` and `cypari2` are optional accelerators; with neither installed, `--kernel python` uses standard Python integers. `--kernel auto` selects PARI if `cypari2` is importable, otherwise Python. The search grows exponentially with the number of D-levels; use a small example first:

```sh
python3 Primorial_iota_Solver_v2_1.py --end-r 4 --max-level 6 --workers 2 --kernel python --outdir ./Primorial_iota_v2_runs --tag demo
```

A smoke run of this command (without PARI or gmpy2) returned `EXACT` values `[1, 2, 2, 3]` for $n=1,2,3,4$. For a longer session, choose `--end-r N`, `--max-level S`, `--workers W`, and optionally `--time-budget-hours H`. To continue a **matching** stopped run, reuse the same outdir/tag and add `--resume`. `--selftest` asks for $N=18$ and checks the first 18 built-in reference values; it can be much more expensive than the four-interval smoke run. Avoid rerunning into an existing tag without `--resume`: output files may be appended to while in-memory state starts over.

The solver writes the following under `OUTDIR/TAG/`:

| File | Meaning |
| --- | --- |
| `iota_min.csv`, `iota_min_table.txt` | Interval bounds, status, proved lower bound, known upper bound, best witness, pair counts. |
| `hits.csv` | Each newly found consecutive-pair witness, its D-level discovery point, actual level, interval, $D$, Pell power $k$, distinct-factor count and prime-complete flag. |
| `state.json` | Checkpoint, completed levels/task masks and per-level statistics. |
| `eps_cache.jsonl` | Cached Pell fundamental solutions for resuming or a larger size window. |

`EXACT` means the displayed minimum has been certified by completed levels; `BRACKET` means a lower and an upper bound are known but equality is not certified; `LOWER` means only a lower bound is known. Blank `iota_min` does **not** mean the interval contains no pair. In `iota_min.csv`, `pc_excluded=NO` means the certified lower bound is greater than $n$, ruling out a prime-complete product in interval $n$; `?` does not assert its existence.

## Archived runs (`Iota_min_Solver_runs/`)

These six files are preserved as supplied. `iota_min_results.json` and `iota_min_results_14.json` are two `Iota_min_Solver v2` runs through interval $n=14$; both report all 14 values and agree. `iota_min_results_29.json` is **named `_29` but its own metadata says `n_max=30`, `end_r=30`**. It reports a witness and a value for 28 of 30 intervals; $n=28$ and $n=30$ are unresolved (`null`). The paired `iota_min_results_29.txt` displays those same gaps. The two `.py` files in the folder are readers/printers for the archived format, not the included current solver.

The archived report records all 30 smoothness-level searches as complete with no discriminant errors or reference mismatches. I independently checked the 28 recorded witnesses in the 30-interval JSON against their displayed factorizations, product-interval bounds, and claimed greatest-prime indices; all passed. These checks establish that the **witnesses are valid upper bounds**. Claims of global minimality additionally depend on completeness of the archived solver's enumeration; the archived raw exhaustive-search trace and its generating source are not included here. Do not interpret the two unresolved entries as exact values or as proof of nonexistence.

## Known issues in the supplied `v2_1` file

- **Unsafe change of `--max-level` on resume.** The solver does not invalidate completed D-levels if the set of allowed primes is enlarged. Example: a fresh run with `--end-r 3 --max-level 2` certifies $\iota_{\min}(3)=2$, but running first with `--max-level 1` and then `--resume --max-level 2` on the same tag leaves interval 3 at `LOWER` with lower bound 3: level 1 is not replayed to find $m=8$. Start a new tag, or use the same prime-limit settings for a resume.
- **Task errors can be certified as complete.** `_task` catches per-discriminant and task exceptions and reports `n_err`, but `run_level` still marks the task/level complete. A nonzero `n_err` must invalidate any `EXACT`/`LOWER` claim based on that level; inspect `state.json` `level_stats` and logs. The code should fail or retain errored tasks for retry instead.
- **Checkpoint configuration matters.** In-progress task masks are stored without the partition parameter `H`, which depends on `--workers * --tasks-per-worker`. Changing either between a mid-level stop and resume can cause masks to refer to different D-subsets. Keep both fixed for a resume.
- **Non-resume reuse of a tag is unsafe.** `hits.csv` and `eps_cache.jsonl` may contain old entries even while `Results` is reconstructed from scratch; choose a fresh tag for a fresh search. The filename examples, internal version (`v2.0`), and the docstring's claim of “18 known values” are stale relative to the `v2_1` filename and 29-entry reference list.

These observations are recorded rather than silently altering the supplied program. In particular, the four-interval smoke test is a finite validation, not a proof that every large run is bug-free.
